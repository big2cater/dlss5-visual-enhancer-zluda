DLSSNRFilter ZLUDA 加速与双引擎多轮降噪发布包 (2026-09-15，包版本 v2026.09.14-v6)

【使用方法】
1. 解压整个文件夹，不要只复制单个 DLL。
2. 将 NVIDIA 官方的 nvngx_dlssnr.dll 放入根目录（与 video_filter.exe / dlssnr_gui.exe 同级目录）。
3. 双击运行 dlssnr_gui.exe（Qt 6 统一现代图形界面；视频批处理与单图增强都在这个窗口里）。
4. 视频处理需要 ffmpeg.exe 和 ffprobe.exe；请确保已安装 FFmpeg 并把 bin 目录加入系统环境变量 PATH。
5. 首次使用请先点击 GUI 中的【预热缓存】按钮预热翻译缓存（进度实时显示在日志窗口，约 20~40 分钟，仅此一次）；
   完成后状态栏显示"缓存已就绪"，即可秒级处理图片/视频。更换程序版本或更换显卡后需要重新预热一次（自动检测）。
   直接跳过预热也能处理，但首次会长时间无进度提示，容易误以为卡死。

【本次修复 (v2026.09.14-v6)】
1. CUDA 层：网络的空输出不再被当作"成功"（一处静默失败）：
   - 现象：evaluation 被接受、却没有产出任何像素时，本层以"成功"返回 ——
     调用方无法把"什么都没跑出来"和"一张好帧"区分开，空结果就这样当成果输出；
     日志里只有一行 "network output: … every byte zero (fully blank)"，没有任何错误提示。
   - 根因（dlss_layer/dlss_cuda.cpp 的 finish_evaluation）：它已经把整张输出读回、
     算出了"每个字节都是零"，然后只写了一行日志，紧接着就 return 成功。
     它还有第二处毛病：这个读回检查被"每进程只做一次"的闩锁管着，
     首次成功读回之后，第 N 帧的空输出就再也没人看 —— 而本层自己的注释写过
     这个竞态是"同样参数八次运行五比三"，即失败可能落在任意一帧。
   - 修复：**每帧**都抽样读回输出与输入（整幅图上均匀取 24 行，各约 24 次行拷贝、
     开销可忽略），判定规则是：输出采样全零、且输入采样有内容 ⇒ 经 set_error 报错
     并返回失败（调用方能看见、能重试）；两者任一读失败则视为"未知、继续"，
     不拿读失败当空输出证据。输出全零、但输入也是空 ⇒ 只是暗场，仍然成功。
     每进程一次的那次**全帧**读回保留下来，只用于详细日志与"部分写入"诊断，
     它的闩锁不再吞掉失败判定。
     这条区分是关键：早先那版"过度敏感的首帧空白判定"正是因为不区分输入而误杀了暗场
     （见 v4 一节）。读回标志改为"读回成功之后"才置位。
   - 验证（在出厂二进制上实跑）：亮帧 exit 0、平均亮度 164、2 遍 1410 ms、
     读回 1 490 689 / 1 843 200 字节非零；全黑帧仍 exit 0（平均亮度 0），
     且其网络输出非零（1 553 704 字节）⇒ 暗场不会被误判为故障。
     视频端到端（同一份出厂二进制，30 帧测试片）：exit 0、blanks=0、
     每帧 66~67 ms（与 gfx11 基线一致）、输出 30 帧、中间帧亮度 164。
     如实说明：新分支只在"网络什么都没产出"时开火，而该故障在本机不复现，
     所以这里能验证的是"不该开火时不开火"；开火之后的行为是代码审查结论。
2. 预热尾部不再可能"无声卡住"，也不会误杀慢机（v6 内二次修正）：
   - 现象（本机实测）：预热长时间停在 "N of M modules translated" 不再前进，看起来像卡死；
     而且超时处理只杀父进程，留下孤儿编译进程继续占着 GPU。
   - 修复：连续 **60 分钟没有任何模块完成**即触发；触发时按 CPU 进度分开处理 ——
     已经停止消耗 CPU 的子进程被结束并计入失败，**仍在消耗 CPU 的暂时只告警、继续等**
     （消息形如 "no module finished for 60 minutes; killed (no CPU progress): …;
     still translating (left running): …"）。之所以要分开：本代码库自己记录过
     "最大的那个模块在慢机上要几十分钟"，10 分钟的死线会**恰好**杀掉健康但慢的翻译。
   - 同时补上"永远不会结束"的那一种：同一个尾部连续 **3 次**死线都没有任何模块完成时，
     幸存者也会被结束并计入失败（消息写作 "killed after 3 deadlines with nothing finishing: …"）。
     计数在任一模块完成时清零，所以"慢但一直在推进"的机器永远够不到它；阈值随预算缩放
     （默认 3 × 60 分钟；若把预算覆盖成 1 分钟，则是 3 分钟）—— 慢机上应当把
     DLSSNR_PRECOMPILE_NO_PROGRESS_MINUTES **调大**，而不是调小。
   - 阈值可用环境变量 DLSSNR_PRECOMPILE_NO_PROGRESS_MINUTES 覆盖（正整数，单位分钟）。
   - 验证：把阈值设为 1 分钟实测，预热在 155.8 s 内收敛并正常完成（exit 0，90 帧，
     结果与正常预热一致）。
3. GPU 自动识别结果写进日志文件（GUI 用户终于看得到）：
   - 以前这些信息只写 stderr 与调试器输出，从 GUI 启动时看不到；
     而"识别成哪块卡、注入或纠正了哪个 HSA_OVERRIDE_GFX_VERSION"正是排查要看的第一现场。
   - 现在同时追加写入 %TEMP%\dlssnr_gpu_autoconfig.log（带时间戳与 pid，便于对比多次运行）。
4. 随包脚本更新：diagnose_gpu.ps1 现在每个 HIP 探针都单独隔离，且不再丢弃 TdrLevel
   （脚本自身的问题，与主程序无关）。
5. 更正上一节里的一个数字：RDNA 4 判据的自测实际为 **28 例**（v5 说明里写作 26 例）。
   重新编译运行：28 例、0 失败，并自带反例对照 —— 旧判据把 RX 7600（Navi 33，0x7480）
   认成 RDNA 4、同时漏掉工作站卡 Radeon AI PRO R9700，新判据两处都正确。
6. 依据 v6 全量代码审查（BUG_REVIEW_2026-09-15.md）修复的其余条目：
   - **并行模式的音频不再可能让整段 GPU 推理白做**：`--parallel` 最后一步拼接所用的
     音频白名单与单进程路径不一致（早先是"除 6 种之外一律原样 copy"），MP4 输出遇到
     dts / truehd 一类无法直接封装的编码时，ffmpeg 会在最后一步拒绝，并**删掉全部分片**。
     现在拼接复用单进程路径的同一份白名单：非 MKV 且不在名单内即转 AAC 192k，
     并打印与单进程一致的 `[audio]` 提示。
     （实测：20 秒 vorbis 音源 + `--parallel 2`，修复前输出音轨仍是 vorbis，
     修复后为 aac、exit 0、blanks=0。）
   - **拼接阶段"音轨格式未知"不再静默丢掉整条音轨**：`audio_codec` 为空（探测没给出结果，
     例如输入根本没有音轨）此前走 `-an` 把音频全部丢掉，而单进程路径在同样情况下是照常
     copy；现在两处规则一致 —— 只有"用户要求不要音频"或探测明确说没有音轨才丢。
     （实测：纯视频输入在 `--parallel 2` 下 exit 0、输出无音轨、无多余告警。）
   - **CPU 运动上传的 `Map()` 失败不再崩溃**：此前它的返回值被丢弃，设备移除时
     mapped 为 null 仍继续 memcpy；现在按同文件其他三处同款写法检查并报错返回。
   - **空白判定阈值笔误更正**：`looks_like_blank_result` 的空白门槛注释写着 0.005，
     而实际常量 `0x191e` 只有 0.0025（0.005 的正确编码是 `0x1D1F`）—— 门槛被砍半，
     峰值落在 (0.0025, 0.005] 的空白帧此前会静默通过判定。已改为 `0x1D1F`。
   - **`flush_and_wait` 只在真正等到时才返回成功**：此前只判 `WAIT_TIMEOUT`，
     事件句柄创建失败时 `WaitForSingleObject` 返回 `WAIT_FAILED` 会**直接返回 true**
     （等于没等就继续，后续 CUDA 读与 D3D12 拷贝可能竞争）。现在只有 `WAIT_OBJECT_0`
     算成功，超时与等待失败分别报错并附设备移除原因；`CreateEventW` 失败在初始化即报错。
   - **GUI 目标补上 `/utf-8`**：与 video_filter / processor_smoke 一致，不再把源码里
     非 ASCII 字面量的编码交给构建机的活动代码页决定。
     （实测：加之前后出厂 GUI 的四个中文界面串都是正确 UTF-8，两者二进制仅 4 字节不同，
     可见中文并未乱码；此项属确定性与卫生性修复。）
7. GUI 与随包脚本的同类修正（同样来自本次代码审查）：
   - **窗口标题的版本号**从 v2026.09.10-multipass 更正为当前版本 —— 用户报问题时引用的
     就是这串，它此前把每一份报告都指向了旧版本。
   - **RDNA 4 提示改用共享判据**（`dlssnr::is_rdna4_gpu`）：GUI 里另抄的一份名单已经漂移，
     漏掉工作站卡 Radeon AI PRO R9700，也完全不知道设备 ID 区间 —— 恰恰是最需要这条
     提示的用户收不到它。
   - **单帧对比与预览的 ffprobe 不再泄漏**：超时后先 kill 再重试（Qt 对仍在运行的进程
     再次 start() 只会警告、不会重启，回退命令根本没跑）；并且同一输入只探测一次，
     预览与正式运行共用结果，不再各起一次。探测超时保持 5 秒是有意的：慢盘确实需要，
     缩短它等于把"卡一下"换成"整段帧数算错"。
   - **fix_tdr.ps1**：备份文件改为带时间戳（固定名会让第二次运行用"已被改过的值"覆盖掉
     用户真正的原始值）；备份写失败时**不再继续改注册表**（新增 `-Force` 表示明确接受
     无备份继续）；TdrLevel=0（TDR 被有意关闭）时，改为先要求输入 YES 才继续。
   - **diagnose_gpu.ps1**：HIP 探测在 `hipSuccess` 但 `count=0` 时不再显示绿色 —— 那正是
     HSA_OVERRIDE 在这块卡上失效的典型形态，显示绿色会让人误判 HIP 侧正常。
8. 第三轮（审查里"安排修"那一档）：
   - **栅栏超时后不再带病继续**（M2）：`State::wait()` 超时/失败，或
     `allocator->Reset()`/`cmd->Reset()` 任一失败之后，管线进入"死态"：后续帧立刻以
     明确错误返回，而不是在一份状态未知的指令列表上按未定义行为继续录制；
     全文 7 处 Reset 现在都检查返回值。
   - **GPU 光流的栅栏等待超时不再被当作成功**（M6）：此前 `WaitForSingleObject` 的返回值
     被丢弃，超时后照样去读一份没人写过的回读缓冲，把垃圾光流当成功送进网络；
     现在超时即返回失败，落到既有的 CPU 光流回退路径。
   - **运动矢量不再沿用上一帧**（M5）：只有真正上传成功才把 motion 纹理绑给网络 ——
     原条件问的是"调用方是否传了 motion"，于是因 pitch/尺寸不匹配而跳过上传的那些帧，
     仍然绑定了装着上一帧数据的纹理（陈旧 MV 比没有 MV 更糟：会把时序滤波拖向不存在的画面）。
   - **`process_raw_rgb48` 补上 pitch 下限守卫**（M4），与 `process()` 同款；
     0 仍按"未指定"处理，仓库内现有调用方行为不变。
   - **D3D12 与自动配置现在选同一张卡**（M3）：选卡逻辑此前分散在三处（自动配置按 AMD 优先、
     `start()` 纯按显存、precompile 固定 HIP device 0），混合显卡机器上会出现
     "D3D12 在用非 AMD 卡、而 ZLUDA 侧全指向 AMD 卡"—— CUDA/D3D12 共享纹理不能跨适配器。
     现在两处调用同一个 `select_primary_gpu()`，且首选卡一旦采纳就不会被枚举中更大的卡顶掉；
     precompile 的 device 0 仍然正确（ZLUDA 暴露的正是这张卡）。
   - **预热计数语义修正**（L12/L13）：子进程消失也会刷新死线基准（此前基准陈旧，死线可能
     因一个已经不存在的子进程而触发）；`WaitForMultipleObjects` 失败的详情不再被末尾的
     计数信息覆盖。
   - **`frame_blit` 初始化失败不再泄漏已编译着色器**（L30）：三处失败路径此前漏放
     `g.vs`/`g.ps`（原始通道连根签名一起漏），现在统一走 `release_partial()`。
   - **顺手清掉已证明无用的代码**（L11 的一部分）：`eval_index`（只增不读）、
     `full_copy_ready`（恒 false）、`image_has_signal`（全仓无调用者）。其余几项
     （`resize_rgb48`、`Channel::clear`、`OutputFrame` 的两个字段、GpuFlow 的 `cb` 缓冲）
     经核对同样无使用点，但删除与本轮修复无关，留待专门的清理提交。

【本次修复 (v2026.09.14-v5)】
1. 修复 RDNA4 显卡预热必然崩溃的问题（重点）：
   - 现象（RX 9060 XT 上报）：RDNA4（gfx12）预热必然失败，日志显示
     "7 of 15 modules could not be translated"，紧接
     `LLVM ERROR: Cannot select: intrinsic %llvm.amdgcn.wmma.f32.16x16x16.f16`，
     进程以 0xC0000409 异常退出；只有 09-09 及更早的版本能在 RDNA4 上工作。
   - 根因：接收原生 WMMA 的分支条件写的是 `>= 11000 && < 13000`，把 gfx12 也圈了进来；
     但 gfx12 上这条内建的操作数形状与 gfx11 不同（gfx11 为 v16f16，gfx12 的选中模式是
     v8f16），指令选择找不到可匹配的模式 ⇒ LLVM 直接中止整个编译，没有任何回退。
   - 修复：把该条件收紧为 `< 12000`，gfx12 退回各 helper 本就带有的通用（软件）路径 ——
     可以正常编译与运行、结果正确，代价是比原生路径慢。
   - 验证（离线完成，不需要 gfx12 显卡）：用 `zoc --arch gfx1201` 编译同样的片段，
     修复前是同一个 `Cannot select` 崩溃、修复后 exit 0，且生成物中 `v_wmma` 数为 0
     （证明确实走软件路径）；`--arch gfx1100` 仍是原生（`v_wmma` ≥ 1）；
     5 个 mma 测试片段在 gfx1100 / gfx1201 下全部编译通过。
     在 RX 7900 XT（gfx11）上复测：新驱动 66 / 67 ms，旧驱动 69 / 70 ms，
     且 30 帧输出与旧驱动**逐字节一致**（PNG SHA-256 相同）—— 即 gfx11 行为未变、无回归。
   - 需要知道的代价：RDNA4 的首次预热会**明显变慢**（软件路径把每条 MMA 展开）；
     帧时间也会明显慢于发布说明里 RX 7900 XT 的 67 ms 一类数字 —— 那些是 gfx11 的实测，
     不是 gfx12 的预期。
   - 下一步（B）：为 gfx12 做原生路径（优先 FP8，RDNA4 有对应硬件指令），
     其片段映射必须用 gfx12 显卡验证，因此作为后续计划。
2. 修复 GPU 自动识别中会误伤 RDNA3 的设备 ID 判据（与第 1 条同批，但影响面更大）：
   - 旧判据把 RDNA 4 认成「device_id 在 0x7480..0x74DF」，而这一段是 Navi 33 的地盘：
     0x7480 就是 RX 7600，同段的还有 RX 7600 XT、RX 7650 GRE、RX 7400（OEM）、
     RX 7600M XT、RX 7600S、RX 7700S 以及 PRO W7600 等工作站卡；
     RDNA 4 的真实 ID 是 Navi 48 = 0x7550、Navi 44 = 0x7590 —— 也就是说这条判据
     一个 RDNA 4 卡都匹配不到，却会把 RX 7600 一类卡当成 RDNA 4，给它们注入
     HSA_OVERRIDE_GFX_VERSION=12.0.1；按下方【驱动更新】一节记录的机制，非 gfx12 的卡
     拿到 12.0.1 后驱动会拒绝加载生成的模块 —— 那些卡会「每个模块都在第一帧之前失败」。
     RDNA2 的设备 ID（0x73BF / 0x73DF / 0x73FF / 0x743F）都更低，不受这条影响。
   - 现在改为按实测 ID（0x7550 / 0x7590）判断；删掉并不存在的型号名 9080 / 9090
     （RDNA 4 没有旗舰，顶配是 9070 XT），并补上工作站卡 Radeon AI PRO R9700。
   - 逐条自测：tools/test_rdna4_detect.cpp —— 26 个真实「型号 + device ID」组合，
     断言该注入的注入、不该注入的不注入（含把 RX 7600 作为回归用例）。
3. 已验证 / 未验证范围（避免把 gfx11 的数字当成通用预期）：
   - gfx11（RX 7000 系 + Phoenix 核显）：已实测，走原生 WMMA；RX 7900 XT @640×360
     单帧 87 → 67 ms，30 帧与改动前逐字节一致。
   - gfx12（RX 9000 系）：本次修复后可以跑，但走软件回退 —— 首次预热明显更慢，
     帧时间也慢于上面这组数字。
   - RDNA2（RX 6000 系：Navi 21/22/23/24 与 680M/610M 核显）及更早的 gfx10：未验证。
     它们同样没有矩阵指令（实测 v_wmma = 0，与 gfx12 一样走软件回退）。

【本次修复 (v2026.09.14-v4)】
1. 单图路径的"明亮门槛"上调（承接 v3）：
   - v3 把单图判定门槛定为线性 0.25，实测发现余量太小：在暴露问题的那一帧上（预告片首个暗帧，
     峰值 0.239）门槛只高出 **4.8%** —— 那不是余量，是巧合。
   - 现提高到线性 **0.35**（sRGB ≈159/255），同一帧余量变为 **47%**；处理器内部同款判定一并同步，
     两处数值保持相等（代码注释里互相注明来源）。
   - 影响：更暗的静帧不会被判为"竞态"（宁可漏报也不误杀）；亮度足够高、却输出全黑的静帧仍会被判出。

【本次修复 (v2026.09.14-v3)】
1. 补齐"空白判定"的同类遗漏（承接 v2）：
   - v2 只修正了视频"处理阶段"的那一处判定；复查后发现**还有三处**同类判据仍在用旧门槛：
     编码阶段的判定、单图路径的判定、以及处理器内部的两道判定（process / process_raw_rgb48）。
   - 现在统一为：视频侧要求"输入明显明亮（>sRGB ≈93/255）+ 连续 3 帧"才判竞态；
     单图侧只有一帧、无法用连续帧区分，改用更高的明亮门槛（线性 0.25 ≈ sRGB 138/255），
     并把判定结果与实测输入峰值一并打进日志，事后可复核；
     处理器内部那道**看不到输入亮度**的检查收窄为只判"全零"（真正的发射失败指纹），
     近零但非零的情况交回给有上下文的判定。
   - 另：视频"处理阶段"的检查不再只覆盖前 ~2 秒，而是**逐帧**生效 —— 开场很暗的片段、
     或较晚才出现的竞态，现在也能被发现。
   - 实测：预告片 120 帧 exit 0 / blanks=0；回归片段 exit 0 / ~106 ms/帧 / blanks=0；
     暗帧单图 exit 0（日志："输入峰值 12517/65535，门槛 13312 ⇒ 未判定为空白"）；
     视频两处门的触发路径分别用临时强制构建验证（连续两帧告警、第三帧中止、退出码 2、blanks=1）。

【本次修复 (v2026.09.14-v2)】
1. 修复"淡入黑场片头被误判为竞态、导致整部影片永远无法处理"的问题：
   - 现象：影片开场是黑场（预告片、片头黑幕等，约 0.2~0.3 秒）时，处理会反复报
     "输出空白而输入有内容（ZLUDA 竞态），交由外层重跑"，以全新进程重试多次，
     但每次都在**同一个帧**失败，最终只能中止 —— 整部影片无法开始处理。
   - 原因：空白判定原先只要求"输入有信号"（任一通道 > sRGB 27/255）。淡入时第一帧刚越过
     这条线，而该帧本身仍接近纯黑、网络的历史缓冲也还是黑的，输出自然低于空白阈值，
     于是守卫把**正常画面**判成了启动竞态。
   - 修复：现在要求输入**明显明亮**（> sRGB ≈93/255，约为空白阈值的 22 倍）且**连续 3 帧**
     都满足，才判定为竞态 —— 真竞态会让每一帧都变黑，而淡入、暗场、历史重置一两帧内即恢复。
     命中时日志会同时打印"输入峰值/65535"，便于事后复核。
   - 实测：此前必然失败的淡入片头片段现已正常跑完；常规片段表现不变（640×360 稳定 ~106 ms/帧、
     无空白告警、退出码 0）。启动竞态本身仍会被正常捕获（已用强制空白构建验证：连续两帧告警、
     第三帧中止、退出码 2）。
